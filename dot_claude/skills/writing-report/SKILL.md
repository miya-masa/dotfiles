# レポートを書く

**このスキルの責務は文章生成ではなく情報設計**。何を書くかからではなく、誰に何を伝え、読後どうなってほしいかから始める。

読み手は結論と判断材料だけが欲しい。書き手の思考過程・背景説明・気配りの補足はノイズになる。一方で、読み手が数字の意味と良し悪しの向きを推測しなければならない資料は、短くても読めない。**削るのは書き手の都合であって、読み方の手がかりではない。**

判断の基準は一貫して**初見の読み手**。書き手は測定条件も指標の定義も覚えているので、自分で読めば必ず読める。**2 回目に読む人の理解度で良し悪しを決めない。**

初見で詰まるのは次の 5 つで、どれも書き手からは見えない。

| 詰まりどころ | 直し方 |
|---|---|
| 指標の良し悪しの向きが行ごとに違う | 差分列を倍率ではなく言葉で揃える（`references/writing-rules.md` ルール 10） |
| 単位・条件・基準が書いていない | 表・グラフの直前の「見方」1 行に置く（同ルール 8） |
| 社内や実装側でしか通じない語 | 読み手の言葉に置き換える（同ルール 7） |
| 桁の多い数値が並ぶ | サマリでは丸める。正確な値は本文の表に置く |
| 何を測ったのか行名から分からない | 行名を対象から始める（「書き込みの〜」「読み取りの〜」） |

文体そのもの（AI 臭・命題型 H2・偏愛語）は `stop-ai-slop-jp` の担当。ここでは情報の設計と並べ方を扱う。

## ワークフロー

| Step | やること | 出すもの |
|---|---|---|
| 1 | 既存文脈の確認 → 不足している「誰に / 何を / 読後どうなってほしいか」だけ対話で確認 | 質問（不足があるときだけ） |
| 2 | report strategy を内部で決定（形式・情報量・構造） | 何も出さない |
| 3 | 素材を人間向けに再構成して執筆 | 初稿（ユーザーには見せない） |
| 4 | 読みやすさレビュー → 修正 | 完成稿 |

Step 1 と 4 を飛ばさない。**初稿をそのまま返さない。**

## Step 1: 誰に / 何を / 読後どうなってほしいか

この 3 つが分かれば執筆へ進む。**それ以上ヒアリングしない。**

| 項目 | 確定すべきこと |
|---|---|
| 誰に | 読み手は誰か。その分野の知識レベル、詳細まで読むか結論だけか |
| 何を | このレポートで最も伝えたい 1 つのこと |
| 読後 | 状況把握 / 技術理解 / 承認 / 判断 / リスク認識 / 次アクション決定 / 記録 |

- **文脈から推測できることは質問しない。** 依頼文・直前の作業・素材の性質で分かるものは仮定して進め、仮定を 1 行添える。
- 質問するときは 1 問ずつ機械的に聞かず、不足分をまとめて確認する。選択肢は 2〜3 個、推奨を 1 つ出す。
- **文書形式は聞かない**（Step 2 でこちらが決める）。
- ユーザーの答えが漠然としているときだけ「読んだ人に最終的に何を理解してほしいか」を深掘りする。

## Step 2: report strategy を決める

### 形式を選ぶ

固定テンプレートを機械適用しない。目的から構成を組む。複数形式の組み合わせも可。

| 読後の期待 | 形式 | 中心に置くもの |
|---|---|---|
| 判断・承認してほしい | Decision Record / Proposal / Recommendation | 結論 → 推奨 → 根拠 → 却下案 |
| 案を選んでほしい | Comparison Report | 判断軸の表 → 推奨 → 各案の制約 |
| 状況を把握してほしい | Status Report / Executive Summary | 現在地 → 差分 → リスク → 次アクション |
| 技術を理解してほしい | Technical Report | 結論 → 仕組み → トレードオフ → 制約 |
| 何が分かったか知ってほしい | Investigation Report | 分かったこと → 根拠 → 未解明点 → 次の一手 |
| 再発防止したい | Incident Report / Postmortem | 影響 → 時系列 → 原因 → 対策 |
| 後から引ける状態にしたい | Reference Document / FAQ | 引きやすさ優先。結論先行より索引性 |

### 読み手ごとに載せる情報そのものを変える

難易度を変えるだけでは足りない。**掲載する情報を入れ替える。**

| 読み手 | 載せる | 落とす |
|---|---|---|
| 経営層 | 結論、ビジネスインパクト、リスク、必要な意思決定 | 実装詳細、計測手法、技術用語 |
| PO / PM | 結論、スコープと期日への影響、判断が要る点 | 内部実装、コード根拠 |
| エンジニア | 結論、技術的根拠、トレードオフ、制約、実装への影響 | 事業説明、一般論 |
| チーム内共有 | 何が分かったか、なぜそう判断したか、次に何をするか | 網羅的な証跡 |
| 自分用の記録 | 事実、数値、再現手順 | 読み手向けの言い換え |

読み手が複数なら、**主読者を 1 人決めて本編を最適化し、他の読み手向けの情報は Appendix へ落とす**。全員向けに薄めない。

### 素材は source material として扱う

入力の調査結果・AI 生成資料・ログをそのまま整理して出さない。何が重要か / 何を捨てられるか / 何を詳細へ移せるかを判断して再構成する。必要なら **Human-facing report** と **Appendix / Evidence** を分離する。

## Step 3: 構成と執筆

### 先頭にサマリを置く

背景説明から始めない。**結論を散文のリード文にもしない。**

最初のセクションは「サマリ」にし、表か箇条書きで出す。

| 伝えたいこと | サマリの形 |
|---|---|
| 複数の観点で A と B を比べた結果 | 観点を行にした比較表。最終列を「どちらが良いか」にする |
| 単一の結論と、その条件・制約 | 結論 1 行 + 条件を 1 行ずつ並べた箇条書き |
| 状況と次アクション | 現在地 1 行 + アクションを 1 行ずつ並べた箇条書き |

```
悪い（背景から始まる）: 今回 A について調査を行った。まず現状を説明すると〜。

悪い（結論が散文）: A は B より 2 倍速く、CPU も 0.62 倍で済む。読み取りも全条件で速い。
                    A が負けるのは低レートの条件だけで、その差は最大 27%。

良い: 観点を行にした比較表 1 つ + 例外と制約を 1 行ずつ並べた箇条書き。
```

2 つ目の「悪い」は結論が先頭にある。それでも読みにくいのは、**読み手が段落を要素へ分解しながら読むことになる**ため。分解を書き手側で済ませて渡す。

背景や調査過程はサマリの後ろに置く。**ただし結論が出ていない調査報告で、無理に結論を作らない**（その場合は「今分かっていること / 分かっていないこと」を先頭に置く）。

### Progressive disclosure

重要な情報 → 判断材料 → 詳細の順に置く。典型は 結論 / 推奨アクション / 重要な根拠 / 判断に必要な情報 / 詳細 / Appendix。固定テンプレートではない。守るのは 1 つだけ。

**途中で読むのをやめても、その時点までで必要な情報が得られる構造にする。**

### 情報に強弱をつける

結論・重要な根拠・リスク・未解決事項・補足・詳細な証拠・調査ログを同じ粒度で書かない。重要なものほど前に短く、詳細なものほど後ろに。

### 見出しだけで大筋が分かるようにする

「概要」「詳細」「検討」「考察」「その他」のような抽象見出しを乱用しない。

```
悪い: ## 検討結果
良い: ## A 方式なら既存システムへの変更を最小化できる
```

全見出しを文にする必要はない。**文書全体のスキャン性を優先する。**

### 表・箇条書き・散文を使い分ける

| 表現 | 適するもの |
|---|---|
| 表 | 複数案の比較、数値比較、メリット/デメリット、条件ごとの差異、ステータス一覧 |
| 箇条書き | 独立した重要ポイント、アクション、リスク、条件 |
| 散文 | 因果関係、判断理由、背景説明、複雑なニュアンス |

何でも箇条書きにしない。**読み手が最も速く理解できる表現を選ぶ。**

### 情報密度を最適化する（文章量ではなく）

必要な情報は残す。落とすのは、同じ内容の言い換え / 不要な前置き / 自明な説明 / 読み手が既に知っている背景 / 結論に影響しない詳細 / AI 特有の一般論 / 「〜について説明します」のようなメタ文章。**少ない文字数で判断材料を失わないこと。**

**密度を上げることは、1 行に詰めることではない。** 上限は**1 行・1 セル・1 項目が単独で読めること**で、それを超えたら分割する。詰め込むと、削ったつもりが読み手の負荷に付け替わる。

| 詰め込みの形 | 直し方 |
|---|---|
| 1 つの箇条書き項目に論点が 2 つ | 項目を分ける |
| 表の列が多く、横に長い | 列を減らして本文の 1 段落へ逃がす。または表を分割する |
| 強調したい箇所が多い | 太字を足さず構造へ逃がす（`references/writing-rules.md` ルール 9） |
| 表の直後にまた補足の箇条書き | 表に入れるか、見出し + 1 段落にする |

### 執筆の詳細ルール

`references/writing-rules.md` を読む。表の作り方、箇条書きの粒度、冗長さの削り方、読み手が知らない言葉の扱い、表とグラフの「見方」、グラフ生成、統計量の落とし穴、事実と推測の分離を Before/After 付きで扱う。**数値や表を含むレポートでは必ず参照する。**

Confluence へ載せるなら `references/confluence.md`。

### 章立ての型（検証レポート）

素材が計測データのときの既定形。他の形式では Step 2 の表から組む。

```
サマリ         表 or 箇条書き。詳細を読まない人がここだけで判断できる。散文で書かない
用語           本文で使う言葉と良し悪しの向き。読み手に前提知識がないときだけ置く
1. 前提        機材・設定・評価指標。表と「タイトル: 値」の箇条書きだけ
2. テストケース 実際にやったことを書く。計画段階の案・優先度は消す
3. 結果        サマリ表 → ケースごとの表と図 → 測定の制約 → 所見（すべて事実）
4. 次にやること 見立て（推測）+ 対策の選択肢 + 未検証な点
5. 運用上の注意 当日ハマったこと
参考           条件の違う既存データなど、本編に混ぜると誤読させるもの
```

サマリの前にリード文を置かない。表か箇条書きから始める。

## Step 4: 読みやすさレビュー

初稿を Step 1 で決めた読み手になったつもりで読み、直してから出す。

**設計**

- [ ] 冒頭 30 秒で要点が理解できるか。結論までスクロールが要らないか
- [ ] 先頭のサマリが表か箇条書きになっているか。散文のリード文になっていないか
- [ ] 最も重要な情報が埋もれていないか
- [ ] 見出しだけを読んで大筋が分かるか。見出し階層が深すぎないか
- [ ] 1 セクションに複数の論点を詰めていないか
- [ ] 詳細を Appendix へ移せないか。この読み手に不要な技術詳細が混ざっていないか
- [ ] 途中で読むのをやめても、その時点までで必要な情報が得られるか

**密度**

- [ ] 同じことを繰り返していないか。同じ数値が 3 回以上出ていないか
- [ ] 表の直後に、表の値を繰り返す文が無いか
- [ ] 背景・経緯・前回からの変更理由を書いていないか
- [ ] AI 特有の冗長な一般論が残っていないか
- [ ] 計画段階の内容（やらなかった案、優先度列）が残っていないか

**形式**

- [ ] 箇条書きが過剰でないか。比較すべき情報が散文に埋まっていないか
- [ ] 1 つの箇条書き項目・1 つのセルに論点を 2 つ入れていないか
- [ ] 表の列が多すぎないか
- [ ] 太字を使っていないか。強調したいことを見出し・列・箇条書きの位置で表せているか
- [ ] 2 文以上の箇条書き項目、1 項目に複数の値を詰めた箇条書きが無いか
- [ ] 表・グラフの直前に「見方」の 1 行があるか（基準・良し悪しの向き）
- [ ] 比較表の差分列で、行ごとに良し悪しの向きを判定し直さずに読めるか
- [ ] 図の説明が、図から読めないことを書いているか
- [ ] 読み手が知らない指標名・専門用語が本文に残っていないか

**数値**（数値を含むときだけ）

- [ ] 推測が結果セクションに混ざっていないか
- [ ] 素材に無い派生値（内訳・単位あたり・合計・比）を自分で作っていないか。作ったなら元の値から検算し、出どころを 1 行添えたか
- [ ] グラフと表の数値が生データから生成されたものか（手打ちしていないか）
- [ ] 1 つの表の中に違う統計量（直接の中央値と中央値の積など）が混ざっていないか
- [ ] 範囲を書いた箇所が、全セルの範囲になっているか（1 行だけ見ていないか）
