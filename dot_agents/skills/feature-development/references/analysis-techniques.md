# 分析手法の詳細ガイド

## 1. 決定表分析（Decision Table Analysis）

条件のすべての組み合わせを列挙し、各組み合わせに対する期待動作が定義されているかを検証する。

### 手順

1. スペックから**すべての条件**を抽出する
2. 各条件の取りうる値を列挙する
3. すべての組み合わせを表にする
4. 各組み合わせの期待動作をスペックから埋める
5. **空欄のセル = 未定義動作 = Gap**

### 実施方法

```
条件1    | 条件2    | 条件3    | 期待動作
---------|----------|----------|---------
値A      | 値X      | 値P      | 動作1（スペックに記載あり）
値A      | 値X      | 値Q      | ???（スペックに記載なし → GAP）
値A      | 値Y      | 値P      | 動作2（スペックに記載あり）
...
```

### 組み合わせ爆発への対処

条件が多い場合（5+）、全組み合わせは非現実的。以下で絞り込む:

- **ペアワイズ**: 任意の2条件の全組み合わせをカバー（多くのバグは2条件の相互作用で発生）
- **リスクベース**: セキュリティ・データ整合性に関わる条件を優先
- **等価クラス**: 同じ動作をする条件値をグループ化

### 必須の追加チェック

決定表を完成させた後、以下の問いを**すべて**確認する:

- **優先順位**: 複数の条件が同時に満たされる行で、どの動作が優先されるか定義されているか？（例: TOTP と パスキー の両方が有効な場合、パスワード認証後にどちらを要求するか）
- **兼用・共有**: 1つの要素が複数の役割を兼ねている場合、その組み合わせで意味が変わらないか？（例: パスキーが「認証手段」と「2FA手段」を兼用する場合、パスキー認証 + パスキー2FA = 実質1要素）
- **属性の変更**: 表の条件値が動的に変更された場合、既に進行中のフローへの影響は？（例: ローテーション猶予期間中にキーのスコープが変更された場合）

### 注意点

- 「条件Aが有効なら条件Bは無関係」と思い込まない。必ず表に書いて確認する
- 否定条件（～でない場合）を忘れやすい。各条件の「無効/未設定/デフォルト」も値として含める

## 2. 状態遷移分析（State Transition Analysis）

システムの状態遷移を網羅し、すべてのイベントに対する遷移先が定義されているかを検証する。

### 手順

1. すべての**状態**を列挙する（初期状態、中間状態、最終状態）
2. すべての**イベント/トリガー**を列挙する
3. 状態×イベントの遷移表を作成する
4. 各セルの遷移先をスペックから埋める
5. **空欄のセル = 未定義遷移 = Gap**

### 実施方法

```
           | イベントA | イベントB | イベントC
-----------|----------|----------|----------
状態1      | → 状態2  | → 状態1  | ???（未定義 → GAP）
状態2      | → 状態3  | ???      | → 状態1
状態3      | エラー   | → 状態1  | → 状態3
```

### チェック項目

- **到達不能状態**: どのパスからも遷移できない状態はないか
- **脱出不能状態**: 一度入ると抜け出せない状態はないか（意図的でない場合）
- **初期状態**: システム起動時・リセット時の状態は明確か
- **エラー状態**: エラー発生後の回復パスは定義されているか
- **並行遷移**: 複数アクターが同時に遷移を引き起こした場合の動作
- **自動遷移の失敗**: スケジュールやタイマーによる自動遷移（期限切れ、自動無効化等）が失敗した場合のフォールバックは定義されているか？（例: 猶予期間終了の自動無効化がジョブ障害で遅延した場合、その間の旧キーの扱い）
- **遷移中の属性変更**: 中間状態にあるリソースの属性（スコープ、権限、設定値等）が変更された場合の動作は？（例: ローテーション猶予期間中にキーのスコープが変更された場合、旧キーと新キーのスコープ整合性）

## 3. 不変条件検証（Invariant Verification）

「常に真であるべき条件」を特定し、すべての操作パスでそれが維持されるかを検証する。

### 手順

1. スペックから**不変条件**を抽出する（明示的なもの + 暗黙的なもの）
2. すべての操作パスを列挙する
3. 各パスの実行後に不変条件が維持されるか検証する
4. **違反するパス = Gap**

### 不変条件の発見方法

暗黙の不変条件はスペックに書かれていないことが多い。以下の問いで発見する:

- 「このシステムで**絶対に起きてはいけないこと**は何か？」
- 「データの**常に満たすべき整合性**は何か？」
- 「セキュリティ上**常に保証すべきこと**は何か？」

### 典型的な不変条件

- **認証**: 「認証済みでないユーザーは保護リソースにアクセスできない」
- **データ整合性**: 「親レコードが削除されたら子レコードも削除される」
- **課金**: 「有料プランの機能は支払い済みユーザーのみ使用できる」
- **権限**: 「管理者権限の操作は管理者のみ実行できる」

## 4. 敵対的思考（Adversarial Thinking）

攻撃者の視点で設計を分析し、バイパスや悪用のシナリオを検証する。

### 手順

1. **保護対象**を特定する（何を守るべきか）
2. **攻撃面**を列挙する（保護に関わるすべてのエントリポイント）
3. 各エントリポイントで以下を問う:
   - 「認証/認可をバイパスできるパスはないか？」
   - 「正規の操作の組み合わせで、意図しない結果を得られないか？」
   - 「前提条件を満たさずに操作を実行できないか？」
   - 「操作の順序を変えたらどうなるか？」
   - 「途中で中断したらどうなるか？」

### 思考フレーム

- **STRIDE**: なりすまし、改ざん、否認、情報漏洩、DoS、権限昇格
- **最小権限の原則**: 必要以上の権限が付与されていないか
- **フェイルセーフ**: エラー時にセキュアな状態にフォールバックするか（オープンではなくクローズド）

## 5. 境界分析（Boundary Analysis）

ビジネスルールの境界における動作を検証する。数値の境界だけでなく、概念的な境界も含む。

### 手順

1. スペックから**ビジネスルールの境界**を抽出する
2. 各境界の「ちょうど」「直前」「直後」の値でテストケースを考える
3. 動作が定義されているか確認する

### 境界の種類

| 種類 | 例 | チェックポイント |
|------|------|-----------------|
| **数量** | 上限10件 | 9件、10件、11件 |
| **時間** | 30日間有効 | 29日目、30日目、31日目、期限切れ直後 |
| **権限** | ロール境界 | 一般→管理者の昇格/降格の瞬間 |
| **状態** | 有効/無効 | 切り替えの瞬間、切り替え中の操作 |
| **空/ゼロ** | リスト | 0件、1件、最大件数 |

## 6. 依存分析（Dependency Analysis）

設計が他コンポーネントや外部システムに対して持つ暗黙の前提を検証する。

### 手順

1. 設計が**依存するコンポーネント**を列挙する
2. 各依存に対して「暗黙に仮定していること」を書き出す
3. 各仮定が崩れるシナリオを検討する

### チェック項目

- この依存先が**ダウン**したらどうなるか？
- この依存先の**レスポンスが遅い**場合は？
- この依存先の**API仕様が変わった**場合は？
- この依存先の**データ形式が変わった**場合は？
- この依存先と**バージョン不整合**がある場合は？

---

## 7. 時間軸分析（Temporal Analysis）

並行操作、タイミング依存、順序依存に関する問題を検証する。

### 手順

1. **並行して発生しうる操作**を列挙する
2. それらの操作が同時に発生した場合の動作を検証する
3. 操作の順序が逆転した場合の動作を検証する

### チェック項目

- 同じリソースへの**同時書き込み**
- **読み取り→判断→書き込み**の間に状態が変わるケース（TOCTOU）
- キャッシュの**有効期限切れ**と更新のタイミング
- 非同期処理の**完了順序**が保証されないケース
- **リトライ**時の冪等性

### 必須の追加チェック: 猶予・遷移期間中の全操作列挙

設計に猶予期間・遷移期間・移行期間がある場合、以下を**すべて**検証する:

1. その期間中に実行可能な**すべての操作**を列挙する（CRUD + 状態変更 + 属性変更）
2. 各操作が期間中のリソースに対してどう作用するか定義されているか確認する
3. 特に以下を見逃しやすい:
   - 期間中のリソースの**属性変更**（スコープ変更、権限変更、設定値変更）
   - 期間中のリソースに対する**同種操作の再実行**（再ローテーション、再招待等）
   - 期間の**延長・短縮**が可能か、その条件は何か
   - 期間終了の**自動処理が失敗**した場合のリカバリ（手動トリガー、リトライ、アラート）
   - 複数の期間が**重複**した場合の優先順位（例: 有効期限と猶予期間がどちらも設定されている場合、どちらが先に効くか）
